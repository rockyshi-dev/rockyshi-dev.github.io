Four LLM load generators against a server with known timing: who delivers the load, and whose numbers to trust

Posted on 2026-10-24
I pointed vLLM bench, GuideLLM, AIPerf and inference-perf at a simulated LLM server whose latencies are fixed, with an idle probe as ground truth. All four report correct numbers up to 200 requests per second. At 500, GuideLLM falls short of the asked load, inference-perf never writes its report, and vLLM bench adds 42 to 50 ms of its own to the TTFT p99.

A serving benchmark is two programs: the server and the load generator. When a number moves, it is usually blamed on the server. I wanted to know how far the four common LLM load generators can be trusted on their own: up to what request rate does each one send the load it was asked for, and does each number it reports match what the server actually did?

To answer that, the server has to be known in advance. So I ran each tool against a simulated server whose timing is fixed, with an idle probe next to it that records what the server did during the same run.

The short answer: up to 200 requests per second, all four deliver the load, and every latency they report matches the server within 10 ms. At 500, vLLM bench and AIPerf still deliver; GuideLLM sends no more than about 400 requests per second and completes about 26,000 of the 30,000 it was asked for; inference-perf sends everything but is stopped before it writes its report. And the tool that delivers at 500 with the least trouble, vLLM bench, reports a TTFT p99 about 45 ms above the server’s.

The setup

The server is llm-d-inference-sim v0.11.2, configured for a time to first token (TTFT) of 200 ms, 20 ms between tokens, no randomness and no queueing (8,192 concurrent sequences). It streams one token per chunk. Every request asks for exactly 50 tokens (max_tokens: 50, ignore_eos: true), so a request takes 200 + 49 x 20 = 1,180 ms.

The tools, at pinned releases, all on the completions API with streaming and a synthetic prompt of about 100 tokens:

Tool Release Constant-rate mode
vllm bench serve vLLM v0.30.0 --request-rate R --burstiness inf, 60 R prompts, one process
GuideLLM v0.8.0 constant profile, 60 s, 24 worker processes
AIPerf v0.13.0 constant arrivals, 60 s, up to 24 workers
inference-perf v0.7.0 constant load, 60 s, 24 workers

The ground truth. A probe, a minimal client in its own process, sends one request every 100 ms during every run and logs its TTFT, chunk gaps and end-to-end time. It is never busy, so what it sees is what the server did. The server’s own request and token counters are read ten times per second, and the probe’s requests are subtracted, which leaves the tool’s.

The machine is a two-socket Xeon Gold 5320 node. The tool gets the 26 cores of socket 0; the server and the probe get separate cores of socket 1; a run is accepted only if processes outside the bench used at most 2% of those cores. Each tool runs at R = 10, 50, 200, 500 and 1000 requests per second for 60 s, three rounds, the tools in a fresh random order at every rate, the server restarted before every run.

At 1000 requests per second the simulator itself is the limit: the probe’s TTFT p99 was 210.1 ms, then 222.8 ms on the retry, above the 210 ms I accept for a server that is not saturated. So 1000 is dropped for every tool, and the valid rates are 10, 50, 200 and 500.

Who delivers the load

Two kinds of tool need two definitions of “delivered”. vLLM bench and inference-perf send a fixed number of requests and wait for all of them, so they deliver if the time from their first to their last completion is at most 60 / 0.95 = 63.16 s. GuideLLM and AIPerf stop at 60 s, so they deliver if they complete at least 95% of R x (60 - 1.18) requests. “Yes” below holds in all three rounds.

Tool 10 50 200 500
vLLM bench yes yes yes yes
AIPerf yes yes yes yes
GuideLLM yes yes yes no
inference-perf yes yes yes no

vLLM bench’s first-to-last completion span was between 59.71 and 60.21 s in every run, so it kept the schedule even at 500. AIPerf completed 29,999 requests at 500 in every round.

GuideLLM at 500 completed 26,309, 26,202 and 26,024 requests, against a floor of 27,940.

The server was not the reason: during those runs the probe’s TTFT p99 was 202.4 to 202.6 ms. GuideLLM itself shows where the requests went. Its JSON export records, for every request, when it was planned to be sent, when it was put on a worker’s queue, when a worker took it off, and when it was sent. Taking the send time minus the planned time:

  • At 200 requests per second, no request is sent more than 0.16 s after its planned time.
  • At 500, GuideLLM keeps the schedule for about the first 20 seconds. From second 20 to 58 it sends only 402 to 409 requests per second, so requests fall further behind the longer the run goes: the median request planned at second 30 goes out 1.9 to 2.6 s late, the latest 15 to 17 s late.
  • The delay is in putting requests on the queue. In round 1, early requests are queued about 4 s ahead of their planned time; that head start is used up by about second 20, and from then on a request is queued late by the same amount it is sent late. Once queued, it is sent about 2 ms later (median), and once a worker takes it, within 0.47 ms (p99).
  • When its 60 seconds are up, GuideLLM stops. The requests it has not sent by then, 3,690 to 3,976 of the 30,000 planned, are never sent. That is the whole shortfall.

So on this machine GuideLLM v0.8.0 with 24 worker processes cannot queue more than about 400 requests per second, and the rest piles up and is dropped at the end.

inference-perf at 500 sent and completed its requests on schedule: 29,998, 30,000 and 29,999 completions within a first-to-last span of 59.9 to 60.1 s. Its log shows the load stage finished after about 62 s, then “Generating Reports…”, and nothing more until the bench stopped it, 180 s after its first completion. At 200 requests per second it wrote its report normally. So at 500 the load went out, but no numbers came back. The one or two missing requests in rounds 1 and 3 were never sent: a worker logged that it could not generate a prompt of exactly 100 tokens after 20 attempts.

Whose numbers to trust

Each tool’s summary was checked two ways: against the tool’s own per-request data (completed count, achieved rate, TTFT and end-to-end p50 and p99), and against the server (TTFT and end-to-end p50 against the probe, the gap between tokens, 50 tokens per request).

Tool agrees differs by its documented definition no reference
vLLM bench 40 0 0
AIPerf 40 0 0
GuideLLM 20 16 4
inference-perf 27 0 13

No cell is wrong. Three things are worth knowing when reading the tools side by side.

GuideLLM’s percentiles are nearest-rank. Its documentation defines the reported percentile as the value at rank ceil(q n) (docs/en/guides/metrics.md), and every GuideLLM percentile here follows that rule. The other three tools interpolate, as numpy does. On the same per-request values the two rules differ by up to 6 µs at p50 and up to 727 µs at p99; the largest gaps are at 10 requests per second, where the tail holds few samples. Read with numpy’s rule, three of GuideLLM’s cells at R = 10 would be wrong; read with its own, all are right. GuideLLM’s achieved rate is time-weighted and has no single count to check it against, and inference-perf’s token gap has no expected value because it re-tokenizes the streamed chunks; together with inference-perf’s cells at 500, where it wrote no report, those are the “no reference” cells.

GuideLLM’s p50 is sometimes one sample off. The floating-point drift described in vllm-project/guidellm#1193 moves the reported p50 one rank above the documented one. Whether it happens depends on the exact request count, so it comes and goes between rounds: here it hit 3 of the 12 p50 cells at 200 and 500 requests per second. The error is 0.24 to 0.72 µs, because neighbouring samples are nearly equal; no one reading a latency would see it.

The tail is where the tool’s own time shows. All four tools’ TTFT and end-to-end p50 match the probe within the bench’s tolerance (10%). But the probe also gives the server’s TTFT p99, and setting each tool’s reported p50 and p99 against the probe’s shows how much of the reported latency is the tool’s own:

  • vLLM bench is within 2 ms of the server up to 200 requests per second at p50, and 10 to 12 ms above it at 500. Its TTFT p99 at 500 is 245.6 to 252.4 ms, while the server’s was 202.7 to 203.7 ms in the same runs: 42 to 50 ms of the reported tail is the client’s. vLLM bench is one process, and its busiest thread is at 0.83 of a core at 500.
  • GuideLLM reports a TTFT p50 3.7 to 4.2 ms above the server at every rate up to 200, and 5.8 to 6.0 ms above it at 500; at p99 the excess grows to 18 to 20 ms at 500.
  • AIPerf and inference-perf stay within 0.5 ms of the server at p50 at every rate they reported, and within about 7 ms at p99.

So a TTFT p99 from vLLM bench at 500 requests per second on this machine is 21 to 24% higher than what the server delivered, and nothing in the tool’s own output says so.

A server bug on the way

While I was building this bench, the simulator’s /metrics endpoint sometimes answered HTTP 500 right after a client had closed streams mid-response: its streaming goroutine wrote to a request context that had already been handed back to the pool. I reported it as llm-d/llm-d-inference-sim#801; the bench retries a failed counter read.

What to take from it

On one two-socket node, with a server that is never the bottleneck below 1000 requests per second:

  • Up to 200 requests per second, any of the four tools gives numbers you can use as they are. Compare GuideLLM’s percentiles with another tool’s only knowing that GuideLLM’s are nearest-rank.
  • At 500, vLLM bench and AIPerf still send the load. For latency at that rate, AIPerf’s numbers match the server; vLLM bench’s tail includes tens of milliseconds of its own.
  • GuideLLM and inference-perf at 500 need a different configuration or a different tool: GuideLLM tops out near 400 requests per second, and inference-perf did not finish its report within 180 s.

Reproduce

The bench is at rockyshi-dev/loadgen-truth-bench. It needs only CPUs and a tokenizer, builds the simulator and every tool at the pinned releases, and writes every raw measurement next to the tables. Every number in this post comes from a run of that repository; the GuideLLM send delays are computed from GuideLLM’s own exports by scripts/guidellm_timing.py in the same repository.
