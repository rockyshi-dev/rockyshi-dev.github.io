TP8, TP4xPP2 or PP8? Splitting a 72B model across eight RTX 4090s without peer-to-peer

Posted on 2026-10-17 Edited on 2026-10-28
Qwen2.5-72B in bf16 needs all eight RTX 4090s of a server without GPU peer-to-peer. Pipeline parallelism gives the fastest first token at every load, tensor parallelism the shortest gap between tokens, and throughput depends on load: vLLM's "PP for higher throughput without NVLink" holds at 32 concurrent requests and fails at 8. Qwen2.5-32B on four of the cards shows the same trade-off.

Updated 2026-10-28. Added the same comparison one size down: Qwen2.5-32B on the four GPUs of one socket, TP4 against PP4, measured the same way (section below; benchmark rockyshi-dev/tp-pp-32b-bench). The 72B numbers are unchanged.

Qwen2.5-72B-Instruct in bf16 has 135.4 GiB of weights. A 24 GB RTX 4090 holds 22.07 GiB under vLLM’s default memory budget, so on a node of eight 4090s the model needs every card. There is no room for replicas. The only decision left is how to cut the model, and vLLM v0.30.0 offers three sensible cuts on eight cards:

  • TP8: every layer split eight ways. Each forward step runs 162 collectives over a ring that crosses both CPU sockets.
  • PP8: eight pipeline stages of 10 layers each. Activations hop seven times per forward pass, once across the sockets.
  • TP4xPP2: each half of the model (40 layers) split four ways over the four cards of one socket. All-reduces stay inside a socket; one hop crosses it.

The node is the one from the first post: PCIe 4.0 x16 per card, no NVLink, and no GPU peer-to-peer on the stock driver, with GPUs 0-3 on socket 0 and 4-7 on socket 1. Every byte NCCL moves between cards is staged through host memory, and one socket carries about 25 GB/s from host to GPU in total.

The answer

Workload: 1,536 prompt tokens in, 128 tokens out, temperature 0, at 1, 8 and 32 concurrent requests. Values are medians over five rounds. Each arm’s round-to-round spread is under 2%, except where a range is given. Bold marks the cell winner: the arm that beat both others in all five rounds.

c Metric TP8 TP4xPP2 PP8
1 median TTFT (s) 1.78 1.80 1.44
1 median token gap (ms) 27.7 44.5 152
8 median TTFT (s) 5.28 3.62 2.19-3.00
8 median token gap (ms) 40.5 52.2 159
8 output throughput (tok/s) 53.7 65.4 41.5
32 median TTFT (s) 9.32 5.94 2.87
32 median token gap (ms) 69.2 68.8 178
32 output throughput (tok/s) 63.7 103 131

Read by metric:

  • Time to first token: PP8 wins at every load. At c = 32 it is 2.87 s against 9.32 s for TP8.
  • Token gap: TP8 is shortest at c = 1 and c = 8. At c = 32, TP8 and TP4xPP2 tie (the ratio was 1.004-1.009 in all five rounds), and both are far ahead of PP8.
  • Throughput depends on load. At c = 8 the hybrid TP4xPP2 wins (65.4 tok/s), and TP8 beats PP8. At c = 32 PP8 wins (131 tok/s).

No split wins everything. If your users wait on the first token, PP8. If they watch tokens stream at low load, TP8. If you run around eight concurrent requests and care about tokens per second, the hybrid.

What vLLM’s documentation says, and how this bears on it

vLLM’s parallelism guide (parallelism_scaling.md, line 23) advises pipeline parallelism on cards without NVLink “for higher throughput and lower communication overhead”. On this node:

  • “Higher throughput” is contradicted at c = 8: TP8 delivers 53.7 tok/s against PP8’s 41.5.
  • It is supported at c = 32: PP8 delivers 131 tok/s against TP8’s 63.7.
  • What PP clearly improves is time to first token, not the gap between tokens. PP8 beats TP8 on TTFT at every load. TP8 beats PP8 on token gap at every load.

So the sentence is not wrong; it is incomplete. Without NVLink, PP buys a faster first token at any load, and higher throughput only once the load is high enough to fill the pipeline.

Two things to read with the table

The token gap is a median. It is the median interval between consecutive output chunks of a request. A median excludes the few long intervals in which another request’s prefill runs. The mean time per output token (mean TPOT) includes those intervals, and under load it orders the arms differently:

c mean TPOT (ms) TP8 TP4xPP2 PP8
8 108 94 174
32 437 268 223

At c = 32 the order reverses: PP8 has the lowest mean TPOT and TP8 the highest. TP8’s median gap of 69.2 ms describes a typical interval. Its mean of 437 ms describes what a stream feels like once the stalls for other requests’ prefills are counted. Every gap verdict in this post uses the median definition.

PP8’s TTFT at c = 8 is a range, 2.19-3.00 s. The closed loop settled into different arrival groupings in different rounds: groups of 2 and 6 in two rounds, 4 and 4 in one, and 3, 4 and 1 in the other two. PP8’s mix of scheduler steps followed the grouping. TP8 and TP4xPP2 repeated one pattern in every round. PP8’s TTFT win holds under every pattern: TP8’s TTFT was 1.76-2.41 times PP8’s.

This comes from the load shape. Every request has exactly 128 output tokens, and the requests of a level start together. So at c = 8 and c = 32 requests finish together and the next prefills arrive together: the load runs in waves.

How it was measured

Arms and what was held equal. Same eight cards, same model files (Qwen2.5-72B-Instruct at a pinned commit), same build of vLLM v0.30.0, same client and the same prompt list in the same order. The KV cache was pinned to 2.25 GiB per GPU in every arm. That gives the same capacity everywhere: 58,976 KV tokens, with no preemption in any measured level. Each worker was bound to the CPUs and memory node of its GPU’s socket, with vLLM’s own NUMA binding. No arm was tuned.

Load. A closed loop at c = 1, 8 and 32, with 30, 80 and 160 measured requests after a warm-up. Every prompt rendered to exactly 1,536 tokens and differed from its first text token on, so the prefix cache never hit. Output was forced to exactly 128 tokens.

Five rounds, rotated. Each round ran all three arms, in an order rotated by one position per round. Each arm was started fresh, ran c = 1, 8 and 32, and stopped.

The decision rule was written before the run. For two arms, a metric and a load, each round gives a ratio. “X is better” means all five ratios favour X by more than 10% (below 0.90, or above 1.10). “No difference” means all five fall within 0.90-1.10. Anything else is unresolved. One noisy round is enough to withhold a verdict. A cell winner must beat both other arms this way. Every verdict above passed this rule in all five rounds.

Gates. A cell counted only if every gate held in that round:

  • Equal KV capacity: 58,976 tokens in every arm, and the preemption counter did not move.
  • Quiet host: no foreign process on any card, and foreign CPU time at most 2% of each socket. In the accepted rounds foreign CPU stayed at or below 0.44%.
  • Placement: every worker’s CPU list and memory node were those of its GPU’s socket.
  • Transport: every NCCL channel went through host shared memory, none through P2P or the network.
  • Clean requests: 1,536 tokens in and 128 out for every request, every request arriving as 128 separate chunks, and no prefix-cache hits.

All 45 accepted cells (3 arms x 3 loads x 5 rounds) passed every gate.

The output check, and a sampler pitfall

vLLM issue #40725 reports TP4 output corruption on PCIe consumer cards in an older release, so I checked that the three splits produce the same text. Before timing, each arm answered 35 prompts (the 30 c = 1 prompts and 5 non-English ones), one at a time, with temperature 0 and the top-5 logprobs at every position. For each pair of arms, I found the first position where they chose different tokens. A difference was benign if each arm’s token sat in the other’s top 5 and the two arms’ choices were less than 1.0 nat apart in logprob. Anything else was called corruption.

Run as first written, this check flags all three arms as corrupt, and the cause is the check itself. The requests left repetition_penalty unset, so the model’s own default of 1.05 applied. vLLM’s sampler takes its argmax over the penalised logits, but the logprobs it returns are raw. The check assumed the emitted token was the argmax of the logprobs it read, and under the penalty that was false: each arm emitted 204-215 of its 4,480 tokens below its own top raw logprob. All 25 “corruption” cases were tokens that one arm rejected because they had already appeared in the prompt or the output.

The fix was one field: repetition_penalty: 1.0 on the check’s requests only, so the emitted token is the argmax of the logprobs returned. I also added a premise test that verifies this, position by position, before the check is read. With the fix, the premise held at every one of 3 x 4,480 positions. Per pair of arms, 15-21 of the 35 prompts were identical, and every other difference was benign, with first-difference margins of at most 0.25 nat. No arm was excluded. The timed runs kept the model’s default sampling settings, identical in all arms.

The lesson: an equality check is only as good as its assumption about what the sampler did. Test that assumption first, and treat the comparison as unreadable if it fails. A gate that fires on its own instrument looks exactly like a gate that caught a real bug.

Where the time goes at c = 1

To explain the c = 1 results, I traced one 1,536-token prefill and 20 decode steps per arm with Nsight Systems. The traced windows reproduce the timed numbers. Decode steps took 27.9 / 44.7 / 152.5 ms (TP8 / TP4xPP2 / PP8), against token gaps of 27.7 / 44.5 / 152.3 ms. Prefill windows took 1.75 / 1.74-1.77 / 1.34-1.42 s, against TTFTs of 1.78 / 1.80 / 1.44 s.

TP8 is read as time in NCCL kernels. In the pipeline arms, a stage posts its next receive as soon as its own work ends, and that NCCL kernel spins until the upstream stage sends. NCCL time there is mostly waiting, not communication. So each pipeline GPU’s window is split into compute, hop transfer, collective time after the last rank arrived, waiting and idle.

per GPU, c = 1 TP8 TP4xPP2 (per stage) PP8 (per stage)
prefill compute 188 ms 178-184 ms 170-179 ms
prefill collectives (after last arrival) 1,556 ms all-reduce (161 x 25.2 MB, median 9.67 ms, about 4.6 GB/s bus bandwidth) 686-704 ms all-reduce inside the stage none
prefill hop between stages none 1.9-2.1 ms; 5.9-6.1 GB/s per GPU pair (12.6 MB, four pairs in parallel) 3.5-8.1 ms per GPU; 11.9-14.8 GB/s per hop (50.3 MB)
decode compute per step 22.4 ms 20.1 (stage 0) / 20.9 (stage 1) ms 18.7 ms (last stage 21.4)
decode collectives per step 5.2 ms 1.6-1.7 ms none
decode hop latency none 9.4-10.0 µs 14-18 µs
  • Why PP8 has the lower TTFT. PP8’s prefill is eight stages of about 175 ms, run one after another, plus seven hops of about 2 ms. TP8 computes for only 188 ms but spends 1.56 s in all-reduce. That all-reduce time matches the NCCL measurement on this node: an 8-rank all-reduce of 24 MiB runs at 4.45 GB/s of bus bandwidth, which predicts 1.59 s for this prefill. TP4xPP2 sits between: each stage computes for about 180 ms and spends about 0.70 s in 4-rank all-reduce.
  • Why TP8 has the shortest token gap at c = 1. In TP8, each GPU reads its share of the weights once per token: 22.4 ms of compute plus 5.2 ms of all-reduce. In TP4xPP2 that happens twice in series (2 x about 20.5 ms + 2 x 1.6 ms), and in PP8 eight times in series (8 x 18.7 ms). The hops cost microseconds.
  • Waiting. In the pipeline arms most of each GPU’s window is spent waiting for its upstream stage. In PP8 decode that is 2.67 s of each GPU’s 3.05 s. At c = 1 this is the pipeline’s serial structure, not communication cost.

TP8’s prefill is the only place where communication dominates: NCCL kernels take 89% of its prefill-step GPU time. Its all-reduce reaches about 4.6 GB/s of bus bandwidth. That figure is not directly comparable with the roughly 25 GB/s one socket moves from host to GPU in a plain copy (the first post): a host-staged ring all-reduce makes several copies per byte and crosses the socket boundary. The trace does not show how the time splits among those steps.

The trace covers c = 1 only, so it does not show why TP4xPP2 wins throughput at c = 8 or why TP8 and TP4xPP2 tie on token gap at c = 32; that needs a trace at those loads.

The same question at 32B on four cards

Qwen2.5-32B-Instruct in bf16 (61 GiB of weights) fits on four cards, so I asked the same question on the four GPUs of one socket (GPUs 0-3): --tensor-parallel-size 4 against --pipeline-parallel-size 4, everything else a vLLM default, same workload (1,536 tokens in, 128 out, c = 1, 8 and 32), same closed-loop client, five rounds with the order of the two splits alternating. The KV pool differs by default (65,872 tokens for TP4, 74,768 for PP4); both hold 32 requests of 1,664 tokens, and no request was preempted in either.

c Metric TP4 PP4
1 median TTFT (s) 0.86 0.67
1 median token gap (ms) 22.1 69.2
1 output throughput (tok/s) 34.9 13.5
8 median TTFT (s) 2.56 1.18-1.38
8 median token gap (ms) 28.7 75.2
8 output throughput (tok/s) 98.9 84.3
32 median TTFT (s) 4.59 1.64-1.79
32 median token gap (ms) 44.5 78.5
32 output throughput (tok/s) 124 243

Bold marks the split that was better in all five rounds, by more than 10% for TTFT and token gap (throughput differs by 17% at c = 8 and a factor of 1.96 at c = 32, the same in every round).

It is the same trade-off as at 72B:

  • First token: pipeline wins. A 1,536-token prompt makes TP4 run 129 all-reduces of 15 MiB through host memory; the NCCL post measured those at 0.71 s on these four cards, which is most of TP4’s 0.86 s. PP4 has no all-reduces and pays its four stages one after another instead.
  • Token gap: tensor parallelism wins by a factor of three. PP4 runs its four stages in series for every token (69.2 ms at c = 1), while TP4 runs one step in which each card reads a quarter of the weights, plus about 2.5 ms of all-reduce per token.
  • Throughput depends on load, and the crossover is the same. At c = 8 TP4 delivers 17% more tokens per second; at c = 32 PP4 delivers twice as many. vLLM’s advice to prefer pipeline parallelism for throughput without NVLink again holds at 32 concurrent requests and not at 8.

PP4’s first-token time at c = 8 and c = 32 again varies by round, for the same reason as PP8’s above: the closed loop settles into different arrival groupings. At c = 8, the two rounds in which requests arrived mostly in groups of four had the lowest median TTFT (1.18 s), and the round in which they arrived in groups of two and three the highest (1.38 s); TP4 repeated one grouping and one value (2.56 s) in all five rounds.

What I expected, and what came out

Before the run I wrote down an expectation that could be wrong. I expected PP8 to win throughput at both c = 8 and c = 32, and the hybrid to land between the pure splits on every metric. The TTFT and token-gap predictions held. The throughput prediction failed at c = 8, where TP8 beat PP8. The hybrid prediction failed too: TP4xPP2 is the outright throughput winner at c = 8.

Scope

Every number here holds for 1,536 prompt tokens to 128 output tokens with fixed output length, bf16 weights, and this node: eight RTX 4090s on PCIe 4.0 without peer-to-peer on the stock driver, across two CPU sockets, running vLLM v0.30.0 with default settings apart from the pinned KV pool and the NUMA binding. The 32B comparison holds for the same workload on the four cards of one socket, with vLLM’s default settings throughout.

Reproduce

The benchmark is at rockyshi-dev/tp-pp-72b-bench. The harness starts each arm, runs the closed-loop client, checks every gate from the raw records, and computes the five-round verdicts from per-request timestamps. Its README has the exact commands. The 32B comparison is rockyshi-dev/tp-pp-32b-bench, built the same way; the 32B numbers above come from a run of it.
